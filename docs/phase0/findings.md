All five boundaries are GO-with-conditions. None is NO-GO, so no NO-GO response from spec §8 applies. The findings change the rev 2 plan in six places, so the scope doc is now rev 3 with one decision-log row per change, each citing this file: 16 ms tick fixed (§5.1); exact native/WASM equality with `-ffp-contract=off` and deterministic collision order (§5.2, §8, risk 2); producers keep history for re-send (§5.4); deterministic collision order and a sim/cosmetic RNG split in Phase 1; null-surface extraction with a link-time MiniCore split (Phase 2); the Qt-for-WASM boundary decided in the Phase 2 spec.

### Verdict calibration

- **S3 is GO-with-conditions, not GO.** The frame-time figure measures the vsync-paced rAF interval at about 120 Hz, so it shows that a 12-box scene holds the refresh rate. It does not show GPU headroom. The smoothness test used the mock's constant-speed circle, so it never exercised acceleration. S5 later rendered the real S1 feed (real braking and acceleration) with p95 10.0-10.3 ms, but only judged smoothness by eye. The apex-gp car was never measured at 12 cars. Conditions: (1) measure GPU cost and interpolation under acceleration with real apex-gp visuals before Phase 3 sets frame budgets; (2) pin one three.js version (apex-gp declares ^0.185.1, the spike pins 0.176.0); (3) render the tick feed too. The spec's S3 criterion is smooth motion "from both feeds", but only the 20 Hz telemetry feed was ever rendered ("From tick feed: not measured in S3"), and S1 committed telemetry-rate samples, not a tick-feed sample (tick feeds are gitignored), so the 62.5 Hz game case is untested.
- **S4 is GO-with-conditions, not GO.** Resume and restart lost 0 events, but only because the replayer could re-send the whole session from seq 0. The relay keeps its log in memory only. After a restart, consumers stall until the producer gets back past their `lastSeq`, and a real producer has to keep its full history or burst-resend it. S4's "Contract v0 amendments needed: none" was right for the mock feed, but S5 then showed that `lap` events from S1 carry no `lapMs`. Conditions: the producer-retention rule (now in scope §5.4) and the decision 6 amendments.
- **S1, S2 and S5 keep their per-spike verdicts.** S1 is repeatable only with the 4 unguarded determinism hacks. Rows 40-42 also change upstream's collision order and row 41 changes which pairs each resolver pass re-tests, so desktop collision behaviour with them is unvalidated. The repeatability evidence covers one track and one seed. S2's exact match covers MiniCore on arm64 only (no Dust car physics, no libm calls from game code, no x86-64). The user confirmed watching S5 end to end on 2026-10-15.

## Decisions

1. **Extraction approach: null surface (`MC_HEADLESS`), not a SimObject/RenderObject split.** S1 ran full 3-lap races (1 car and 12 cars) with no GL context and no offscreen fallback. Physics reads only CPU-side geometry: surface width, height and z come from the decoded image and the metadata, never from a texture. None of the 42 hacks fakes state that physics reads. A full split would mean rewriting `MCObject`, whose pimpl owns both shape and view. Phase 2 instead turns the 23 GL guards (rows 1-23) into a link-time split of MiniCore into a GL-free core and a renderer library. It also does the bounded refactors from rows 24-42: a `SimConfig` instead of the `Game` singleton, no `Renderer::instance()` in factories, and particles, audio and number plates as render-side subscribers.
2. **Tick length: 16 ms confirmed.** S1 and S2 both ran at a 16 ms fixed tick on MiniCore's whole-millisecond `stepTime(int)` API with no physics API change. The units check out: velocity is world units per tick, so m/s = |v| × 0.05 × 1000 / 16 = |v| × 3.125, and position-derived speed ÷ emitted |(vx, vy)| has median 1.0016. Headless throughput is about 17-40× real time, so the tick fits the budget. Phase 1 still has to show feel parity in the desktop game. Fix the off-by-one in tick labels: the state after N steps is tick N, `tMs = N × 16`.
3. **Determinism tolerances (from S2):** the primary contract is exact native↔WASM equality: position 0, heading 0, discrete events exact. This needs two preconditions: (a) `-ffp-contract=off` and no `-ffast-math`/`-Ofast` on every native translation unit that feeds the sim (WASM needs no flag); (b) deterministic collision ordering. S2-A compiled MiniCore from `spike/s2-wasm`, which already carries S1's hack rows 39-42 (collision pairs, resolver pairs and contacts sorted by creation serial), so the exact match was only ever measured with that ordering; Phase 1/2 must keep rows 39-42 or an equivalent ordering by per-world stable IDs. Fallback, only if native cannot use the flag: position 0.002 m and heading 0.001 rad. These hold only for sessions shorter than the first discrete-event flip seen (tick 17313 in 6 runs); the worst case before it was 1.34 mm, about 1.5× under the limit. Discrete events are always exact, never toleranced. Under default flags, long sessions are chaotic, so compare events and keyframes only. This was measured only for MiniCore on arm64. Phase 2 must rerun the diff with Dust car physics (`car.cpp`, `tire.cpp`, gearbox) and game-code libm calls before relying on it. Game code calls libm directly (`std::atan2` at `ai.cpp:70`, `std::pow` at `car.cpp:231`), and macOS libm and Emscripten's musl are different implementations. If that rerun shows libm-dependent drift, sim code moves to one portable math implementation (for example `MCTrigonom`-style lookup tables); if that is not enough, native-vs-WASM checks fall back to discrete events plus keyframes (scope §5.2, §8).
4. **Qt status: Gui still needed. "QtCore at most" has not been shown.** The S1 harness links Qt Core, Xml and Gui. Gui is needed for `QImage` decode and scaling in `MCSurfaceManager` and for `QColor`, and `QtGui.framework` itself links `OpenGL.framework`. The harness's own objects reference 0 GL symbols. S2-A showed the MiniCore physics core is Qt-free and builds under Emscripten unchanged relative to `spike/s1-headless` (it needs that branch's `MC_HEADLESS` guards from rows 1-23, and S2-A also compiled its collision-order rows 39-42; S2 added no source edit of its own). S2-B counted 128 undefined Qt symbols across 25 translation units of the harness (strings, signals/timers, XML, files, settings, images) but did not build them for WASM (disk floor). Estimates, not yet validated: Qt for WebAssembly (qtbase Core/Xml/Gui) about 0.5-1 day plus 1-2 GB, against about 3-5 agent-days to replace Qt. A third route is a Qt-free WASM core fed by the JSON track/asset pipeline Phase 2 already plans. The Phase 2 spec chooses between them (scope rev 3, Phase 2). Before that, it checks Qt 6.12 wasm against the emsdk 4.0.10 pin and a QCoreApplication-only Node harness.
5. **apex-gp reuse cost: low for the car model; licence still blocks committing.** `createCarModel` lifted cleanly with a closure of 7 files (`car/{chassis,livery,materials,wheels}.js` at about 7.8k lines, `core/{assets,rng}.js`, `textures/procedural.js`) and no engine or game state. One car, built once, took about 1.7 s. Costs: it needs a DOM canvas for procedural textures; three.js versions must be unified (apex-gp declares ^0.185.1, the spike pins 0.176.0); the model's nose points to −z, so it needs a heading offset; build time and memory for 12 cars with per-car materials are unmeasured. The Dust `.trk` → three.js tile scene path works (665 tiles and 28 nodes for Monza; the coordinate mapping is scene x = x_m, z = −y_m, heading = rotation.y). Nothing from apex-gp is committed until the ISC notice and ownership are confirmed (scope §2, risk 6). The reuse table in scope §6 stays as it is.
6. **Contract v0 amendments** (apply to `contracts/telemetry-v0` before the Phase 1/2 emitter):
   - `lap` event data gains `lapMs` (schema and S1 emitter). S1 emits `{lap}` only, so the tower's "Last lap" column stays empty (S5).
   - `speedKmh` is defined as true speed, `|(vx, vy)| × 3.6` in m/s terms. The game's `speedInKmh()` (×2.75 display tuning) reads about 12 % low, so either derive `speedKmh` from velocity or rename the display value (S1).
   - Tick numbering: tick N is the state after N steps of 16 ms. S1's labels lag one step (S1).
   - `progress` is continuous `(nodeIndex + fraction) / nodeCount` through the line, from the sim. S1's lap rolls over on entering checkpoint 0's box, so the last ~4 % of each lap is never reported, which breaks time-at-position gaps near the line (S1).
   - `pos` before the first checkpoint is the grid slot. `Race::position()` is 0 until checkpoint 0, and the emitter's clamp to 1 masked that: every car reports `pos` 1 at tMs 0. The grid order in S1 is reversed against the driving direction (car 0 at the rear but labelled pole), a harness id-to-slot bug to fix in the Phase 2 emitter (S1, S5).
   - `sessionId` is unique per run. Both S1 samples share one, so a relay that already holds the session ignores a replay (S1, S5).
   - Transport semantics (relay now, gateway in Phase 4): the producer keeps unacknowledged history and re-sends from the relay-reported `lastSeq` (S4). The Phase 0 relay already replays every logged event plus the latest snapshot to a consumer that connects without `from`: a missing `from` becomes -1 (`relay.mjs:46` in tag `phase0-spikes-main`), and `SessionHub.attach` sends `log` plus `latestSnapshot`. It keeps only one snapshot, not a snapshot history, so the render must tolerate starting from a single snapshot. After a connect or reconnect it needs a short buffer of live snapshots before it can interpolate. This single-snapshot replay explains why S5's frame count restarted near 0 after a reload; it is not a relay gap (S4, S5).
   - No change to the snapshot shape for rendering: S3 used only `tMs`, `cars[].id`, `x`, `y`, `heading`.
   - Already in the committed v0 schema but not in Phase 0 spec §5: an optional top-level `wallMs` (producer wall-clock epoch ms, used for S4/S5 latency), and `result.classification[].bestLapMs` is nullable (`integer | null`).
   - Field names to reconcile in schema v1: v0 uses `seq` and `tick` and has no `buildVersion`, while scope §5.4 names `sequence`, `simulationTick` and `buildVersion`.
