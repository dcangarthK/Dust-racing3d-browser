## S2 — Native vs WASM drift

- Verdict: GO-with-conditions. The MiniCore physics core builds under Emscripten unchanged relative to `spike/s1-headless` and is bit-identical to native (state and per-tick collision counts, 6/6 runs) when native is built with `-ffp-contract=off`. "Unchanged" means no S2-specific source edit: `spike/s2-wasm` branches from `spike/s1-headless`, so S2-A compiled MiniCore with S1's `MC_HEADLESS` guards (hack rows 1-20, the Graphics guards) and its deterministic collision ordering (rows 39-42, pairs and contacts sorted by creation serial). The exact match was only measured with that ordering in place. With default native flags the two diverge, and in one 20000-tick run the divergence became a discrete-event difference and then chaotic. S2-B (full Dust harness under WASM) was not attempted; see below.
- S2-A physics scenario (12 objects, 3000 ticks @16 ms, seed 42, 105 collision events, walls and box-box contacts, friction, seeded force and torque):
  - native (Apple clang 16 arm64, Release, default flags) vs wasm: first divergent tick 2, max pos err 6.2e-5 units (3.1e-6 m at 0.05 m/unit), max angle err 7.7e-5 deg
  - native `-ffp-contract=off` vs wasm: first divergent tick none, max pos err 0, max angle err 0, identical yes (all 36000 lines, every field, byte-for-byte after `%.9g`)
  - sanity: native vs native self-diff identical; native vs native `-ffp-contract=off` diverges at tick 2 with exactly the same error as native vs wasm, which attributes the whole drift to FMA contraction (arm64 clang fuses `a*b+c` by default; wasm has no FMA)
- Sweep (`evidence/s2-sweep.txt`, from `sweep.sh`; each run is native default, native `-ffp-contract=off` and wasm, state diff plus per-tick collision-count streams):
  - nofma vs wasm: identical state (every field, every tick) and identical per-tick collision counts in all 6 runs.
  - native default vs wasm, collision totals and per-tick counts: equal in 5 of 6 runs; in seed 42 / 20000 ticks the default native run diverges (540 collisions vs 541 for both nofma and wasm, first per-tick difference at tick 17313). So discrete events are NOT guaranteed exact under default flags.
  - Different seeds/sizes (default native vs wasm max pos err): seed 1, 3000 ticks, 12 objs, 55 collisions: 3.1e-5 units; seed 7, 20000 ticks, 12 objs, 555 collisions: 0.0188 units (0.94 mm), 0.0257 deg; seed 99, 10000 ticks, 48 objs, 1616 collisions: 0.0144 units (0.72 mm), 0.0201 deg.
  - Controlled run length (seed 42, 12 objects, default native vs wasm; collisions 105 / 270 / 540): 3000 ticks 6.2e-5 units, 7.7e-5 deg; 10000 ticks 1.24e-4 units, 1.84e-4 deg; 20000 ticks 54.6 units, 11.3 deg (arena is 2000 units wide, so that is a different trajectory, not rounding noise).
  - Growth curve (per-tick error, not a running max, `evidence/s2-native-vs-wasm-20000.csv`): about 6e-5 by tick 3000 and 1.2e-4 by tick 10000 (slow, roughly linear in this stretch); then a step at tick 12475 where the error goes from 1.2e-4 to 9.1e-3 units in one tick (about 75x, probably a contact; the event stream of this run was not saved, so that is an inference), peaks at 2.68e-2 units at tick 12490, then settles near 1.3e-2 by tick 13000 and stays there until tick 17313, where the collision sequence diverges, then 0.13 at 17320, 1.04 at 17340, 14 at 18000, 37 at 19000).
- Interpretation: bit-identical is achievable with flags (`-ffp-contract=off`, 6/6 runs, up to 20000 ticks and 1616 collisions). Without the flag the error is at the 1e-4 unit level for runs up to about 10000 ticks, but it is not bounded: a single event can amplify it by about two orders of magnitude (75x at tick 12475, probably a contact), and in the one run where a contact outcome flipped (tick 17313) the trajectories separated completely within a few hundred ticks. Run length and contact density are confounded in the sweep (seed 99 with 1616 collisions has a smaller error than seed 7 with 555), so the data do not show a simple relation to collision count; what they do show is that each contact is a potential amplifier and that one flipped contact outcome ends comparability. Treat default-flag native vs WASM as chaotic for long sessions.
- Determinism contract (scope §5.2): the primary contract is exact equality of position, heading and discrete events between native and WASM, which was only achieved with two preconditions: `-ffp-contract=off` on the native side (6/6 runs), and deterministic collision ordering (rows 39-42, or an equivalent ordering by per-world stable IDs), which every S2-A build carried. Provisional fallback, only if native cannot be built with that flag: position 0.002 m and heading 0.001 rad are valid only up to the longest run measured without a discrete-event flip; the measured worst case before any discrete-event flip is 0.0268 units = 1.34 mm (seed 42, tick 12490, ticks 0-17312) and 4.5e-4 rad (about 1.5x below the 2 mm fallback, so little margin), and the flipped run reached 54.6 units (2.7 m) and 11.3 deg, so no tolerance holds for long sessions under default flags. Discrete events must not be given a tolerance: under default flags they diverged once in 6 runs.
- Recommended native build flags for parity: `-ffp-contract=off` on every translation unit that feeds the simulation (MiniCore and the game's car/AI/physics code), and no `-ffast-math` or `-Ofast`. The WASM side needs no flag (Emscripten does not contract without relaxed-SIMD).
- Hack log: S2-A needed no MiniCore or Dust source change beyond those already on `spike/s1-headless` (of those, it compiles rows 1-20 and 39-42; the Asset and Text rows 21-23 are outside its source glob), so there is no new row in `dependency-map.md`. MiniCore Core, Physics and Graphics (minus `mcobjectfactory.cc` and `mcmesh.cc`) compile with `emcc` under `-DMC_HEADLESS` and link to a Qt-free binary (the native one links only libc++ and libSystem). The two excluded files are CMake exclusions in `spikes/s2-wasm/CMakeLists.txt`, not source edits: they include `MCAssetManager`, which pulls `Text/` and Qt asset loading, and nothing in the scenario references them. `mclogger.cc` needed no guard: it only includes QDebug under `Q_OS_ANDROID`.
- Caveats for S2-A: the machine for native and WASM is the same arm64 Mac, so this says nothing about x86-64 native (which does not fuse unless `-mfma`/`-march=native` is passed). The scenario exercises `MCWorld`, collisions, friction and rotation. It does not run the Dust car physics (`car.cpp`, `tire.cpp`, gearbox) or anything that calls libm (`sin`, `cos`, `atan2`, `pow`) directly from game code, so libm differences between macOS and Emscripten's musl are not measured here.
- S2-B full harness: blocked, not attempted. Qt symbol inventory of `s1_headless` (`nm`, 128 undefined Qt symbols across 25 translation units, `evidence/s2-qt-symbols.txt`, per-TU in `evidence/s2-qt-by-tu.txt`). Symbol-group counts (by leading class): QString 22, QObject 14, QImage 12, QtPrivate 7, QTimer 7, QDomNode 7, QTextStream 6, QSettings 6, QPainter 6, QVariant 5, QPixmap 5, QDomDocument 4, QMetaObject 3, QFile 3, QDir 3, QCoreApplication 3, QArrayData 3, QTranslator 2, QRegularExpression 2, QDomElement 2, others 1 each. Groups: strings (QString, QRegularExpression, QTextStream), signals/timers (QObject, QMetaObject, QTimer, QCoreApplication, QTranslator), XML (QDom*, used by the track, mesh, surface and font config loaders), files (QFile, QDir), settings (QSettings, QVariant), images (QImage, QPixmap, QPainter, QColor, used by `mcsurfacemanager.cc` and `graphicsfactory.cc`).
  - Why not attempted: after the S2-A builds `df` showed 12.31 GiB free, which clears the controller's 12 GB threshold by 0.3 GiB only. Installing Qt for WebAssembly (1–2 GB) would drop free space below the 12 GB floor the repo's own `tools/bootstrap.sh` enforces, and `pipx`/`aqtinstall` are not installed. I read the ruling as requiring headroom for the install and stopped at the inventory. A controller who reads it literally can order the install; no work was lost.
  - Recommendation: (b) Qt for WebAssembly (`wasm_singlethread`, qtbase only: Core, Xml, Gui) rather than (a) replacing Qt. Replacing is the bigger job: XML config loaders (4 TUs plus `trackloader.cpp`, the heaviest user with 32 symbols), QSettings, QTimer/QObject signals in `race.cpp`/`timing.cpp`/`difficultyprofile.cpp`/`pit.cpp`, and QImage-based surface loading and `graphicsfactory.cpp` painting. I estimate about 3–5 agent-days for (a), against about 0.5–1 day for (b) plus 1–2 GB of disk. Open risks for (b): Qt 6.12 wasm needs a specific emsdk version (we pin 4.0.10; not checked against Qt's table), Qt's WASM platform layer is browser-oriented so a `-sENVIRONMENT=node` QCoreApplication-only harness is unproven, and data files need `NODERAWFS` or `--preload-file`. A cheaper alternative if only the simulation core must run in the browser: keep Qt out of the WASM build entirely, as S2-A did, and feed it a pre-parsed track description (JSON) produced natively.
