### How it was run

- `node relay.mjs` (8787), `npm run dev` in `spikes/s3-render` (5173), then `node replay.mjs <s1-monza-12car>` with the tower tab on `http://localhost:8787/?session=<id>` and the render tab on `http://localhost:5173/?track=monza&live=ws://localhost:8787/watch?session=<id>&cam=chase|map`.
- The `&cam=...` after the unencoded `live=` value is parsed by `URLSearchParams` as a separate param, so `live` carries only `ws://.../watch?session=<id>`. That works for this URL shape but means `from=` cannot be appended to `live` without percent-encoding.
- Replay ran to `replay: done`; final tower seq 2468, 36 lap events. The tower was last read after the replay ended.

### Observations (S1 contract and tower hazards seen during the run)

1. **`lap` events carry no `lapMs`.** S1 emits `data: {lap}` only; the tower reads `msg.data.lapMs`, so the "Last lap" column stays "—" for the whole S1 race. The mock feed has `lapMs`, so S4 never exposed this. `lapMs` is not in `schema.json` either, so the schema, the S1 emitter and the tower disagree. Fix before Phase 1: add `lapMs` to the `lap` event in the schema and the S1 emitter, or derive it in the tower from event `tMs` deltas.
2. **S1 grid order is reversed against the driving direction.** At the start all cars have `heading` π (driving -x), car 0 is at the largest x (rear of the grid physically) and car 11 at the smallest (front). S1 labels car 0 as `pos` 1 and every car `pos` 1 at tMs 0. The tower therefore shows car #11 leading and #0 last from the start. This is a grid-placement or id-to-slot issue in the S1 harness, not a coordinate-mapping error: cars are correctly placed relative to the track. Pole position in the data (car 0) is the last car to the line in the render.
3. **Tower speeds show S1's `speedKmh`.** It reads about 12% low versus `hypot(vx, vy)` (known S1 hazard; not re-measured here). After the cars finish, the tower shows 49 km/h for cars still circulating; the cars appear to keep driving after the chequered flag (read from the tower at seq 2468, not checked in the S1 data).
4. **Progress skip and tick lag (known S1 hazards).** Not visible at tower granularity. The `progress` skip of the last ~4% of each lap would affect gap computation near the line; not isolated in this run.
5. **Route polyline has visible gaps** in `cam=map` (for example near the north-west corner and between diagonal nodes). That is how S3 draws route nodes (segments between listed nodes), not an S1 or S5 fault.
6. **Both S1 sample files share one `sessionId`** (known). Replaying the same file into a relay that already holds the session will find nothing to send (replay resumes after the relay's `lastSeq`), so the relay was restarted before the recorded run. Not separately exercised.
7. **Live-mode page**: loading `?live=` still fetches the default 4.7 MB mock feed first (the `loadFeed` call precedes the live block, as the brief specifies), so the page shows "loading…" for a moment. After a mid-race reload the render's frame count restarted near 0 and grew at about 20 per second, which suggests `/watch` without `from` delivers only new frames (inferred from the HUD frame count, not checked in `relay.mjs`). Fine for a spike.
